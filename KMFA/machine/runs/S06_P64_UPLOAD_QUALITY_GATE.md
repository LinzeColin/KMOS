- 依赖门：`T-S06-01` / `T-S06-02` / `T-S06-03`，三份证据均在库
- 无直接 AC（`acceptance_ids: []`）——它是 **Stage 质量门**，验的是前三项在压力下是否仍成立
- pass_gate：**阈值内 SLO 通过，数据不变量和隔离边界无失败**

## 与 P6.1–P6.3 的分工

那三项证明「功能对」，这一项证明「**在真实失败和高负载下仍然对**」。
所以每个场景都不测功能，测的是**压力/故障中不变量还成不成立**。

三条不变量贯穿全部场景：

1. **原件不被损坏** —— 任何失败路径之后，既有 artifact 摘要必须仍对得上；
2. **隔离边界不被跨越** —— 任何并发/竞争下，A 的字节不得进入 B 的 workspace；
3. **配额不被绕过** —— 并发开会话时，各自看在额度内、加起来超额，必须被挡住。

## 任务包点名的场景 → 各自能击穿哪条不变量

| 场景 | 击穿的是 | 结果 |
|---|---|---|
| 并发（6 路同时写一个 workspace） | 原件不被损坏 | 成功者摘要属于真实上传之一；失败者零残留 |
| 配额竞争（100 会话 × 6MiB vs 512MiB 额度） | 配额不被绕过 | 放行总量未超额，且确有会话被 429 |
| 断网（**每个分片边界都断一次**） | 原件不被损坏 | 逐次向服务端问偏移续上，最终字节精确一致 |
| 慢速（30 字节一片、30 次请求） | 可用性 | 期间另一 workspace 照常可用——未全程持锁 |
| 扫描积压（4 种恶意形态连投） | 恶意逃逸=0 | 全部 422，`artifact` 保持为 None |
| 对象存储不可用 | 原件不被损坏 | 503，不留半成品 |
| 跨 workspace 推分片 | **stop_condition** | 404，持有者进度不受影响 |
| 长时 soak（12 轮独立循环） | 状态泄漏 | 每轮均成功——sidecar/暂存/配额预留都被回收 |
| 失败路径后原件守恒 | 总不变量 | EICAR、MIME 欺骗、超限依次触发后，原件字段逐一未变 |

## 交付物

`upload benchmark` / `negative matrix` / `capacity thresholds` 合成一张
compact receipt：`receipts/S06_P64_UPLOAD_QUALITY_RECEIPT.json`，**7032 字节**（上限 64KiB）。

合成而不是各出各的，是因为它们回答同一个问题的三面——「压得住吗」「挡得住吗」
「边界在哪」。分开出的话读的人要自己拼，而拼错的代价是把「某一面没测」看成「都测了」。

receipt 里两处刻意的做法：

- **预期与实测分两列。** 预期一列是从任务包阈值原文抄下来的，实测一列由工具现场跑测试填。
  合成一列写就只剩自我确认——只有分开摆，才可能出现「预期与实测不符」这一格。
- **容量阈值读自代码常量，不手抄。** 手抄的数字会和实现悄悄分家，分家之后 receipt 就在说谎。

benchmark 只测**本任务引入的那段开销**（逐片 sha256 + 整体复核），不测网络与磁盘：
那两样由环境决定，放进 receipt 会让不同机器上的数字看起来像回归，其实只是换了台机器。

## receipt 为什么放在 `runs/receipts/` 而不是 `runs/`

`render_human.render_05` 会扫 `machine/runs/*.json`（非递归）投影成
文档「**旧业务**最近 5 条运行记录」表。receipt 属于 v1.5.2 任务包线，
放进去会混进旧业务记录表——语义上就不对，而且因为字段不符会渲成一行空的 `| ? | | |`，
双平面渲染一致门当场红。

这一处按「只作等价识别或增量适配」办：**不改渲染器、不改任务包**，
只把自己的产物放到不会自我错标的位置。子目录不被非递归 glob 扫到。
