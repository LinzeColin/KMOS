## 阈值与落点（逐条对应，不合并陈述）

| 验收阈值 | 落在哪 | 为什么必须这么做 |
|---|---|---|
| 未知/高风险仅附件；执行成功=0 | `disposition_for()` **白名单** | 黑名单永远漏，而漏掉的那个正好是能在浏览器里执行的那个。Content-Type 一并改写成 `octet-stream`，只加 `attachment` 不足够 |
| 超限**在写入预算前**拒绝 | `plan_session()`，开会话时唯一准入点 | 等分片进来再算时字节已落盘，可用必然失败的上传反复占空间 |
| 篡改漏检=0 | `validate_chunk()` 逐片**先验后写** | 只验整体摘要的话坏片已落盘，且分不出是哪一片坏，续传退化成整传 |
| 恢复成功率=100% | 进度落 sidecar + 每片 fsync；`GET .../uploads/{id}` 可查 | 进度只在内存里的话，进程一重启客户端只能从头再来 |
| 重复对象不可控增长=0 | `dedupe_decision()` 在**收字节之前**按内容摘要判 | 放到完成时再判，重复内容已经完整传过一遍，增长已经发生 |

## 实现

- 新增 `app/resumable_upload.py`：纯判定，无 I/O 依赖，便于被阈值直接测。
- `app/walking_skeleton.py` 新增三个路由：开会话 / 查偏移 / 收分片。
  鉴权**复用既有 `_authorize`**，不另起一套——新路由自建鉴权是存在性泄露的常见来源。
- 会话状态用 `.part` 旁的 sidecar JSON（先写临时文件再原子改名），不动 SQLite schema：
  阈值要的是「进程重启后仍能问到正确偏移」，sidecar + fsync 已满足；
  任务包这一项未要求 schema 变更，按「只作等价识别或增量适配」办。
- 配额在既有 `_artifact_capacity_usage` 之上加**未完成会话的已声明字节**，
  否则并发开多个会话可以整体超额（每个单看都在额度内）。

## 过程中被自己的检查抓到的三处（如实记录）

1. 篡改用例的夹具两串长度不同（11 vs 12）——我在用例里写的自检断言当场抓住。
   长度不同就分不清是摘要拦的还是长度拦的，测试会形同虚设。
2. 查重 SQL 写成 `content_sha256`，真实列名是 `sha256`。查询抛错被 `_store()`
   兜成 **503 storage_unavailable**——一个列名错误伪装成了「存储不可用」。
3. 无凭据用例原本断言 401/403，实际返回 404。**代码是对的**：
   401/403 等于确认「这个 workspace 存在」，未认证者连这点都不该知道。已改测试并写明理由。
