# S07 / P-S07-03 · T-S07-03 —— 把有副作用的 GET 导出改为受控命令

- 依赖门：`T-S05-03`（`S05_P53_CONSISTENCY_STATE.md`）、`T-S07-01`（`S07_P71_DOWNLOAD.md`）——均在库
- 绑定验收：`AC-DL-003`（TEST-DL-003）、`AC-DL-004`（TEST-DL-004）
- pass_gate：**有副作用 GET=0；同幂等键唯一结果；任务资源有上限**
- stop_condition：无法区分旧 GET 是否已触发不可逆财务操作

## stop_condition 先处置，再动手

旧 `GET /api/报告中心/导出` 的副作用是往**只追加**的导出登记册写一条记录，外加一条审计。
它不动钱、不改财务事实，且登记册每条都带 sha256——**哪些导出发生过、内容是什么，逐条可查**。
所以停止条件不成立，迁移可以进行。

若它当初改的是财务事实，正确做法是停在这里，而不是先迁移再对账。

## 先找，再改：枚举而不是读代码

AC-DL-004 要的是「枚举 GET/HEAD 前后状态 diff」。读代码找 `write` 找不出三类东西，
而这三类恰好是真会出事的：写在被调用的库里、写在异常路径上、写是将来某次改动加进来的。
所以比对**磁盘上的真实状态**：每条读路由打一次，前后各拍一张快照。

**64 条读路由，命中 1 条**：

```
GET /api/报告中心/导出 是读请求却改了业务状态：
    [app-state] 新增文件 kmfa_app_state.sqlite3
```

### 这个测法第一版是错的，值得记下来

第一版跑出 **64 passed**——包括那条真有副作用的。原因有两个，各自独立：

1. **快照范围太窄**：只盯 `KMFA/machine`，而导出登记写在 `KMFA_APP_STATE_DIR`。
   状态有几个落点就得盯几个；盯漏一个，等于给那个落点发了张免检证。
2. **路由压根没执行**：这条路由有必填 query 参数，不带就 422 被挡在门外，
   函数体一行都没跑。**测试「通过」了，覆盖是零。**

第二条更值得警惕：**一盏覆盖为零的绿灯，比一个红灯危险得多**——红灯会被修，
绿灯只会被信任。现在断言里明确写死「422 即判失败」，并说清该去补什么。

## 为什么 GET 不能有副作用，不是洁癖

- **GET 会被别人替你按**。浏览器预取、链接预览、爬虫、代理预热、用户手抖刷新，
  每一次都往登记册里落一条「导出过」。登记册是交付事实的依据，被噪声灌满就不再是依据。
- **GET 应当可缓存**。一个既产生业务记录又可缓存的端点语义自相矛盾：
  缓存命中时记录没产生，未命中时产生了，而调用方无从知道自己撞上哪一边。
- **成本**。渲染 PDF 不便宜。挂在 GET 上等于把昂贵操作放在人人可无限触发的位置。

## 幂等键的第二条规则才是关键

- 同键 + 同请求 ⇒ 返回同一任务，**一个字节都不重新渲染**；
- 同键 + **不同**请求 ⇒ 409，绝不执行。

第二条常被漏掉，而漏掉它幂等键就是摆设：客户端复用一个键去要另一份报告，
系统「幂等地」返回上一份——它拿到一个**自己没要过的东西**，且一切看起来正常。
所以请求内容指纹化并与键绑死；指纹用 `sort_keys` 规范化，
免得字段顺序不同把正当重试变成 409。

任务 id 由 `(owner, 幂等键)` 摘要得出、**不含随机数**，
所以「同键返回同一任务」不依赖任何查表是否成功。owner 进 id，
是因为幂等键由客户端自取，不能假设全局唯一。

## 同步执行，以及这对「取消」意味着什么

今天任务在 POST 里同步跑完，不排队。据此说清边界，不含糊：

- **取消**只对非终态任务有意义。同步执行下任务在响应返回时已是终态，
  于是取消恒返回 409 并**如实报出当前状态**。
  AC-DL-003 要的是「取消/失败/过期状态**确定**」——确定，不是「总能取消」。
- 换成真 worker 时状态机一行不用改：`queued → running → succeeded/failed/cancelled`
  本来就是为排队写的，只是今天 queued 停留时间为零。

写清楚是因为「有 job 接口 = 异步」是个太自然的误读。

## 四种「拿不到制品」必须分得清

它们对调用方意味着完全不同的下一步，混在一起就只能靠猜：

| 状态 | 码 | 含义 |
|---|---|---|
| 不存在 | 404 | 从来没有过 ⇒ 检查自己的 id |
| 未完成 | 409 | 还在跑 ⇒ 等 |
| 失败 | 409 + 原因 | 跑过但炸了 ⇒ 看原因 |
| 过期 | 410 | 曾经有、已经没了 ⇒ 重新创建 |

**失败的任务永远不会变成 expired**：把失败也标成过期会掩盖失败原因，
而原因正是排查时唯一有用的东西。

**过期在读的时候算，不靠定时任务改状态**：靠定时任务的话，
它没跑的那段时间里系统会拿着过期制品当有效的发。

## 资源上限（无界并发 = 0）

`MAX_CONCURRENT_JOBS=2`、`MAX_JOBS_PER_OWNER=200`、`MAX_ARTIFACT_BYTES=64MiB`、
`ARTIFACT_TTL=24h`。HTTP worker 数**不算**上限——它只管「同时多少请求」，
不区分请求贵不贵；贵的操作要自己的闸。另有一条用例守住这些值不被改成 0 或天文数字
（两者都等于没有上限）。

## 旧端点：410，响亮地停用

迁移的已知风险是「旧客户端无提示失败」。所以不静默改行为，而是 410 +
响应体直说替代路径怎么调（含「要带 Idempotency-Key」）。

**不选「留着但不再登记」**：登记本身是这条端点存在的理由之一。
一个不登记的导出端点看起来还能用，却在悄悄制造「发出去了但没记录」的报告——
比停用危险得多。

## 既有契约测试：迁移，不删不弱化

8 条既有用例断的是旧 GET。它们断言的性质——三格式真渲染、水印去不掉、
hash 只追加、表头带等级三元组、审计留痕——**必须继续成立**，只是换了产出端点。
用一个薄适配器（POST 建任务 → GET 取制品）保持**断言原样**，
因为改断言就分不清「迁移」和「顺手放宽」了。

水印那条更强了一层：那些「看起来能关水印」的参数在新端点上**根本无法表达**，
比「传了也没用」更硬。仍逐个跑一遍，锁住「将来有人把它们加回请求体」。

`export_jobs` 进状态表清单而不是绕过——那条用例的意义正是「不许有没进清单的写」。
