# S07 / P-S07-02 · T-S07-02 —— Range、断点续传与可验证批量 ZIP

- 依赖门：`T-S07-01`（`S07_P71_DOWNLOAD.md`）——在库
- 绑定验收：`AC-DL-002`（TEST-DL-002）
- 阈值：**Range 语义正确；续传 hash 一致；ZIP 项目无丢失/覆盖/路径穿越；失败可重试**
- pass_gate：Range/续传 hash 正确；ZIP 无丢失/覆盖/穿越；**资源受控**
- stop_condition：**批量实现需要把整个归档放入单进程内存**

## stop_condition 决定了实现形态，不是事后检查项

归档写到磁盘临时文件、逐块产出，任何时刻常驻内存只有一个 64 KiB 块。
500 个条目与 5 个条目的内存占用没有差别。两条断言把它钉死：

- 计数读取：源文件的每次 `read()` 都 ≤ chunk_size（若某处 `read()` 了整个文件，当场暴露）；
- `tracemalloc` 峰值：500 条目共 ~10 MiB，峰值 **< 4 MiB**。

用标准库 `zipfile` 而非手写 ZIP 结构：本地文件头、数据描述符、中央目录、ZIP64 切换，
每一处写错都表现为「大多数解压器能开、某一个不能」——最难查的一类缺陷。
手写唯一能换来的是省掉一个磁盘临时文件，不值。

## 「续传 hash 一致」不是 Range 本身能保证的

本任务最容易做漏的一处。制品 v1 共 1000 字节，客户端拿到 0-499；
此时内容变了；客户端接着要 500-999。两段拼起来**既不是旧版也不是新版**，
而且长度对、状态码对、没有任何一层会报错。

防线是 HTTP 早就给好的，本实现全部落地：

- 响应带**强 ETag**（制品 sha256——内容变则 ETag 必变，这正是强验证器的定义，不加 `W/`）；
- 客户端续传带 `If-Range`；服务端发现不匹配就**回 200 整份**而不是 206 片段；
- 只支持 ETag 形式的 If-Range，**不支持 HTTP-date**：秒级分辨率会留一个一秒宽的损坏窗口。

失败方式从「静默损坏」变成「多下一次」。

## 三处实测撞出来的东西

### 一、框架自带一套 Range，会在我选择「不处理」的分支上接管

Starlette 的 `FileResponse` 自己解析 Range。整份分支交给它，等于同一个请求头被解析两次，
而它的判断和本仓三处不一致：

| 情形 | 本仓 | Starlette |
|---|---|---|
| `bytes=nonsense` | 忽略，回 200（RFC 9110 要求） | **400** |
| 多段 | 回 200 整份（防放大） | `multipart/byteranges` |
| `If-Range` | 只认强 ETag | 还接受 `Last-Modified` |

**恰好在我认为最安全的那条路径上，行为不是我写的那个。**
改法是整份与片段走同一条流式产出路径，不再用 FileResponse。
代价是失去 sendfile 优化，换来只有一套语义。

### 二、续传天生是多次请求，而防滥用层按请求数计

一个大文件分 20 段取回，在 10 秒窗口里和导出滥用没有区别，会触发工作量证明。
**这不是测试环境的怪癖，真实客户端一样会撞上。**

处理方式：不关防滥用、不放宽阈值，测试**照规矩解开挑战**——
顺带证明了断点续传与防滥用可以共存，而不是二选一。

排查过程中发现测试必须走 `https`：设备 cookie `__Host-kmfa_device` 带 `Secure`，
在 `http://testserver` 上会被 httpx 拒收，于是每个请求都被判成新设备，
挑战绑定的 `actor_tag` 每次都变，**客户端永远解不开**。
用 http 测出来的续传行为不是生产行为。

**留下的摩擦（不在本任务修，但不假装不存在）**：防滥用按请求数计费，
而续传的成本其实在字节数。真正的修法是让部分内容请求按字节计入预算，
那要动 S03 的防滥用层，不在 T-S07-02 范围。批量 ZIP 那条路正是为此存在——
一次请求拿走一整批，不必发 N 个请求。

### 三、一个 workspace 只能有一个制品，这是 schema 级不变量

`artifacts.workspace_id` 从 `0001_legacy_walking_skeleton.sql` 起就带 `UNIQUE`。
所以 **HTTP 批量下载今天最多只能装一个条目**——不是被限流，是数据模型不允许更多。

于是 AC-DL-002 点名的 **50/500 文件批量只能在归档层证**：
500 条目零丢失、逐项 hash 复核、峰值内存与归档大小无关，全部通过。
HTTP 层证的是这一层自己的职责：鉴权、上限拒绝、流式、审计。

放开这个约束要改数据模型 + 迁移 + 保留策略，属 S02/S03 范围。
**范围不缩，但也不越界去改别人的地基。** 这条边界写成了一条用例
（`test_one_artifact_per_workspace_is_a_schema_invariant`），
让后来的人不必读迁移文件、也不必到生产上才发现。

顺带记两笔观察，都不在本任务修：

- `MAX_ARTIFACTS = 1` 这个常量只出现在对外播报的策略契约里；真正拦人的是
  硬编码的存在性检查 + schema 约束。**声明的上限和执行的上限是两套东西**，
  今天说的是同一件事，改了常量却不会改变行为。
- 第二次上传**开得成**（201），撞墙发生在 `complete`。小文件无所谓，
  大文件就是白传一遍才被拒。

## ZIP：三类「无声丢文件」都堵上了

「无丢失/覆盖」不是数条目数就能证的，碰撞判定必须站在**解压端**：

- **大小写** —— macOS/Windows 默认不区分，`Report.xlsx` 与 `report.xlsx` 归档里是两个、落盘是一个；
- **Unicode 规范化** —— macOS 用 NFD，多数来源用 NFC，`é` 两种写法字节不同、看着一样、解压碰撞；
- **结尾点与空格** —— Windows 静默去掉，`a .txt` 与 `a.txt` 因此碰撞。

碰撞键 = NFC 归一 + 去尾点尾空格 + casefold。判碰撞用它，写进归档的仍是可读名。
重名后缀用 ` (2)`、` (3)`，和主流文件管理器一致。

**归档端的 zip-slip 方向和上传端相反**：我们是生产者，只要把 `../../etc/passwd`
写成条目名，任何没做防护的解压器都会被我们打穿。所以条目名写入前剥掉一切路径成分。
与 `upload_quarantine.safe_filename` 的分工不可互换：上传端**检测**（有问题就隔离，
用户可以改名重传）；归档端**强制**（文件早已入库、属于用户，因为名字不好看就排除在外，
那叫「丢失」，正是 AC 禁止的）。改写连同原名一起进 manifest，没有任何东西悄悄发生。

## 「失败可重试」做成了可验证的性质

可重试要有意义，得能判断「重试出来的和原来是同一份」。所以归档是**输入集合的纯函数**：
条目稳定排序、时间戳钉死在 ZIP 纪元 1980-01-01、权限位钉死。
于是重试 = 逐字节相同 = 归档 sha256 相同，可以直接断言。

取消是异常而不是「返回一个短归档」：半份 ZIP 能正常打开、条目少而已，
用户不会知道它被截断了。先写 `.partial`、成功才 `os.replace`，
中途出错磁盘上不会留下**看起来完整**的归档。

清单同时写进归档（`_kmfa_manifest.json`，名字预占，用户同名文件不会被覆盖）：
归档离开本系统后响应头就没了，自带清单是它唯一还能自证的东西。
