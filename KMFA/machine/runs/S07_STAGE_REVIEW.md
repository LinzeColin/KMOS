## 3. 本阶段最值得记的一件事：两次「测试全绿但什么都没测」

同一类失效在本阶段出现了两次，两次都是我自己写的测试。记下来不是自责，
是因为**这类失效的表现和一切正常完全一样**，不写下来下次还会犯。

**第一次（TEST-DL-004 找有副作用的 GET）**：跑出 64 passed，
包括那条真有副作用的 `GET /api/报告中心/导出`。两个独立原因：

- 快照只盯 `KMFA/machine`，而导出登记写在 `KMFA_APP_STATE_DIR`；
- 那条路由有必填 query 参数，不带就 422 挡在门外，**函数体一行都没跑**。

**第二次（同一份枚举）**：`app.include_router()` 的产物是 `_IncludedRouter`，
没有 `.path` / `.methods`，`getattr(..., "")` 兜底成空串后被跳过——
**整个 walking-skeleton 路由组被静默丢掉**。守卫用例没抓到，
因为它只查「总数 ≥30 + 两条已知路径」，而那两条恰好都在顶层。

> **一盏覆盖为零的绿灯，比一个红灯危险得多。** 红灯会被修，绿灯只会被信任。

三条对策已经落进代码，不是写在文档里的决心：

1. **422 一律判失败**，并在断言里直说该补什么参数；
2. **守卫按路由组点名**，不只数总数——少一组的表现和正常完全一样，
   除非你专门去问那一组还在不在；
3. **白名单条目必须被证明**：两个惰性建出的 `.sqlite3` 配了一条用例
   打开库逐表数行，任何一行都判失败。没有它，白名单就成了
   「把真实副作用洗白成已知情况」的地方。

## 4. 三个「不是省事，是有意为之」的边界

**不做 thumbnail / pdf preview**（T-S07-01 补 T-S06-03 的缺口时）：
它们必须把不可信字节喂给图像或 PDF 解码器，而那类库的历史漏洞几乎全是
「构造畸形文件触发解码器」——引入它们等于把 T-S06-02 挡住的东西从后门放进来。
理由写进代码与 415 响应体，**不留白**：留白会让后来的人以为「忘了做」，
于是补上它，把守住的边界重新打开。

**不引入签名 URL**（T-S07-04）：其整个风险面——泄露即长期可用、撤销要等过期、
CDN 会缓存——通过不引入它来消除。一条用例把「不存在」钉住：
哪天有人加了签名参数它会红，逼着补齐重放与过期测试。

**不放开 `artifacts.workspace_id` 的 UNIQUE**（T-S07-02）：
一个 workspace 结构上只能有一个制品，所以 HTTP 批量今天最多装一个条目。
AC 点名的 50/500 因此在归档层证（零丢失、逐项 hash、峰值内存与归档大小无关）。
放开它要改数据模型 + 迁移 + 保留策略，属 S02/S03——
**范围不缩，但也不越界去改别人的地基。** 这条边界写成了一条用例。

## 5. 留下的摩擦（如实记，不在本阶段修）

**防滥用按请求数计，而续传的成本在字节数。** 一个大文件分 20 段取回，
在 10 秒窗口里和导出滥用没有区别，会触发工作量证明。真正的修法是
让部分内容请求按字节计入预算，那要动 S03 的防滥用层，不在 S07 范围。
批量 ZIP 那条路正是为此存在——一次请求拿走一整批，不必发 N 个请求。

**`MAX_ARTIFACTS` 是声明的上限，不是执行的上限。** 真正拦人的是硬编码的
存在性检查 + schema 约束。今天两者说的是同一件事，但改了常量不会改变行为。

**第二次上传开得成（201），撞墙发生在 `complete`。** 小文件无所谓，
大文件就是白传一遍才被拒。
