## 「字节不一致=0」怎么证

**逐字节比对**，不能只比大小或只比 checksum 头：

- 只比大小 —— 换掉中间一个字节，大小不变；
- 只比 checksum 头 —— 那是**服务端自己说的**，它可以和实际下发的内容不一致。

所以每个用例都拿下载回来的**实际字节**重算摘要，再与上传时的原始内容比；
另有一条专门断言「自报 checksum == 实发字节摘要」。

## 派生物：只做 text extract，明确不做 thumbnail/preview

不是省事，是 T-S06-03 的 stop_condition 顶着：**「处理器需要执行用户文件中的代码或宏」即停止**。

- text extract 对 `text/plain` / `text/csv` / `application/json` 只做**字节解码 + 截断**，
  没有格式解析器，也就没有解析器漏洞面；
- thumbnail / pdf preview 必须把不可信字节喂给图像或 PDF 解码器，
  那类库的历史漏洞几乎全是「构造畸形文件触发解码器」——在本仓引入它们，
  等于把 T-S06-02 挡住的东西从后门放进来。

**理由写在代码与响应体里，不留白。** 留白会让后来的人以为「忘了做」，
于是补上它——把守住的边界重新打开。要做的前置是隔离进程/沙箱与资源上限，
那属于另一个任务，不在 T-S06-03 范围。

派生物**按需生成、不落库**：它是原件的纯函数，重算比存一份便宜，
而且不存就不存在「派生物与原件不同步」这种状态——
T-S06-03 要保的「血缘断点=0」在这里退化成恒真。

## 比阈值更严的一处，有意为之

AC 只要求「高风险格式不内联」，本实现**一律 attachment**，
连白名单内的安全类型也不内联。理由：「一律 attachment」不需要任何判断就成立，
因此不存在「判错一次就内联了」的窗口。另有一条测试锁住**两处策略同向**——
上传侧判「仅附件」的，下载侧不得内联，防的是两个模块各判各的、某天一边放宽了另一边不知道。
