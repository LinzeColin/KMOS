# 压测节拍：每 30 分钟挑**一个**最久没跑的技能跑一遍（KMFA_SWEEP_RUN=1 标成压测跑）。
#
# 替代原来「部署后一口气跑 13 个」的做法——那个当天把线上打下线三次，
# 最长 5.5 分钟；nice + 拉长间隔都不够，因为问题不在参数在形状。
# 单跑一个是正常负载（排程本来天天这么跑），13 个背靠背才是突发。
# 半小时一跳、六个多小时覆盖全部，从没跑过的几小时内就会被碰到。
# 都在 24 小时内跑过时挑不出东西，这一跳什么都不做——而那是**常态**：
# 日排程的技能一天内会自己再跑、永远不够格被挑，节拍精确地只碰周/月/没排程的那几个。
# 闸值是七天模拟挑出来的拐点（原来 6 小时跟「13 个技能 × 半小时 = 6.5 小时」共振，
# 每一跳都触发、重活一天跑四遍——详见 pick_stalest_skill.py 里的表）。
# 一天 48 跳、只有 13 个技能，绝大多数跳都该是空的。所以末尾的 `|| true` 不是装饰：
# 少了它，「正常的空跳」会让整行以非零退出，cron 每半小时记一笔像失败的东西，
# 真失败就淹在里面了。
*/30 * * * *  root SK=$(python3 /opt/kmfa/KMOS/KMFA/tools/pick_stalest_skill.py 2>/dev/null); if [ -n "$SK" ]; then KMFA_SWEEP_RUN=1 nice -n 19 /opt/runtime/run_skill.sh "$SK" >> /var/log/kmfa/cron.log 2>&1 || true; fi

# 项目成本「重新计算」请求：App 在 app-state 卷放时间戳，这里每分钟比一次。
#
# 为什么绕这一圈：App 与 skills 是两个容器，App 里没有 run_skill.sh、也不该有——
# 真让 App 去跑克隆私有库解析上千张表的活，就是把 2026-07-28 那次
# 「压测把线上打下线」原样重演，只是换了个触发器。
#
# 为什么比时间戳而不是「先删后跑」：两个卷的读写方向是刻意反着的——
# app-state 是 app 可写、**skills 只读**（daily-backup 读它打包备份，「绝不写」）。
# skills 删不掉那个标记。第一版把标记放日志卷想着好删，结果 app 对日志卷只读，
# 线上直接 503。所以：标记里是请求时刻，这边在自己可写的卷上记「处理到哪」，
# 标记比记录新就跑。跑的过程中再点一次不会被吞掉——时间戳又变新了。
* * * * *     root R=/var/lib/kmfa/state/.project_cost_refresh_requested; S=/var/log/kmfa/project_cost/.last_refresh_handled; if [ -f "$R" ] && { [ ! -f "$S" ] || [ "$R" -nt "$S" ]; }; then mkdir -p "$(dirname "$S")"; cp -f "$R" "$S" 2>/dev/null || date -Is > "$S"; KMFA_SWEEP_RUN=1 nice -n 19 /opt/runtime/run_skill.sh project-cost-refresh >> /var/log/kmfa/cron.log 2>&1 || true; fi
